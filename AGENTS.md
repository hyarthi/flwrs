# AGENTS.md

Instructions and a map of the repo for LLM coding agents.

## Rules for agents

- **All LLM instructions go in `AGENTS.md`.** Don't create or edit tool-specific files such as `CLAUDE.md`, `.cursorrules` or `.github/copilot-instructions.md`. If a subfolder needs its own instructions, add an `AGENTS.md` in that folder.
- Keep this file up to date when you add, move or remove modules, crates or plugins.
- The repo is a Cargo workspace (root `Cargo.toml`). Run `cargo build/test/clippy --workspace` from the root, or `-p <crate>` for one crate. There's one `Cargo.lock` and one `target/` at the root.
- Dependency versions live only in `[workspace.dependencies]`. Crates reference them with `<dep>.workspace = true` (plus extra `features` if needed). Package metadata (version, edition, rust-version, license, repository) and lints are inherited the same way. The exceptions are the crates published to crates.io on their own: `flwrs-plugin` (the SDK, 0.0.3 so far) and `flwrs-trellis` (the plugin developer toolkit, 0.0.1 so far). Each has its own `version` in its `Cargo.toml`; bump it for each release (a published version can't be reused), and keep the workspace dependency's `version` for `flwrs-plugin` equal to it (crates.io needs it for `flwrs-trellis`). Their crates.io pages are `plugin/README.md` and `trellis/README.md`.
- **Releases:** each release of `flwrs-plugin` gets an annotated git tag `v<version>` (e.g. `v0.0.3`) on the `main` commit it was published from, pushed to GitHub. `flwrs-trellis` depends on `flwrs-plugin`, so when both change, publish `flwrs-plugin` first. Order: commit and push, `cargo publish -p flwrs-plugin --dry-run`, `cargo publish -p flwrs-plugin`, then `git tag -a v<version> -m "flwrs-plugin <version>" <commit>` and `git push origin v<version>` (tag only after the publish succeeded). Publishing and pushing tags are irreversible: only do them when the user asks. New Rust plugins go under `plugins/` and must be **added to `members` in the root `Cargo.toml`**. Members are listed explicitly on purpose: with a `plugins/*` glob, any folder under `plugins/` without a `Cargo.toml` (such as a non-Rust plugin) would break every cargo command.
- Crates use Rust edition 2024 (the latest stable edition) with `rust-version = "1.94"` (set by sqlx 0.9; raise it only when a dependency needs it). `unsafe` code is denied workspace-wide (`unsafe_code = "deny"`). The **only** exception is `app/src/modules/supervisor/process/windows.rs` (Windows API calls for stopping plugin processes), allowed at its module declaration; every `unsafe` block there has a `// SAFETY:` comment. Don't add `unsafe` anywhere else, and don't widen the exception without asking.
- **Platforms:** the server must run on all mainstream OSes: Windows, macOS, Linux and the common Unixes (the BSDs, illumos). OS-specific code goes behind `cfg(unix)` / `cfg(windows)` with a fallback for other targets (see `supervisor/process/`), never assumptions such as `/bin/sh` or signals in shared code. Tests that spawn shell scripts are `cfg(unix)`. Prefer std over helper crates where std covers it, e.g. `std::sync::LazyLock` rather than `lazy_static`.
- `plugin/` generates Rust from `plugin/schema/*.proto` with `prost-build`, using a bundled `protoc` (`protoc-bin-vendored`), so no system install is needed. `app/` does the same for its own file format, `app/schema/scene_file.proto` (`.flwr` scene exports); the proto conventions below apply there too, and it's versioned separately (the version in the file header).
- Before finishing, run `cargo clippy --workspace --all-targets` and `cargo test --workspace`, and keep clippy clean. `flwrs-app` has four default features: `mapping-lua` (Lua edge mappings, via `mlua` with vendored Lua 5.4), `otel` (the OpenTelemetry telemetry sink: vendored OTLP protos + reqwest), `telemetry-file` (the local file telemetry sink; flate2) and `remote` (remote plugins: remote launch mode, `remote_id`, pre-shared tokens, the `[hub.tls]` listener and mTLS; rustls with the `ring` provider + x509-parser). `flwrs-plugin` has one, `tls` (the SDK's TLS client); the workspace depends on it **without** default features, so crates opt in (`http_sink` does; `flwrs-app`'s `remote` feature does). When touching anything feature-gated, also run `cargo clippy -p flwrs-app --all-targets --no-default-features` and `cargo test -p flwrs-app --no-default-features` (and `cargo clippy -p flwrs-plugin --all-targets --no-default-features`), and keep them warning-free (for telemetry, also `--no-default-features --features telemetry-file` and `… --features otel`: the `otlp-json` file format needs both) (code only used with a feature gets `#[cfg_attr(not(feature = "…"), allow(dead_code))]` with a reason). Tests whose expectations differ use `#[cfg(feature = "…")]` / `#[cfg(not(...))]`; tests that create remote nodes are `#[cfg(feature = "remote")]`.
- **Plugin types are called "type", never "kind"** (DB columns, manifest fields, Rust names, API fields, docs): `plugins."type"`, manifest `"type": "SINK"`, `PluginType`. In Rust, a field that can't be called `type` is named `plugin_type` and mapped with `#[serde(rename = "type")]` / `#[sqlx(rename = "type")]`.
- **Naming of time and date fields** (DB columns, proto fields, Rust struct fields, JSON keys): use a `_time` suffix for timestamps (date + time) and `_date` for date-only values. Never `_at` / `_on`. Follow the existing verb-stem pattern: `create_time`, `update_time`, `start_time`, `finish_time`, `enqueue_time`. The suffix tells you the type at a glance.
- `ideas/` holds design notes for possible future work, one Markdown file per idea, each with a status line at the top. They aren't specs: check with the user before implementing one, and update or remove the note when an idea is adopted or dropped.
- **Dev runs** use `config.dev.toml` from the repo root (`cargo run -p flwrs-app -- --config config.dev.toml`). All runtime data (DB, installed plugins, spool files, logs) goes under `./.data/`, which is gitignored. When adding a setting that writes to disk, point it at `.data/` in `config.dev.toml`. Never write runtime data into the source tree.
- App write transactions start with `BEGIN IMMEDIATE` (`conn.begin_with(...)`): a deferred transaction that reads and then writes fails with "database is locked" instead of waiting when another connection is busy.
- Migration scripts run inside a transaction, so they must not contain their own `BEGIN`/`COMMIT`. Write SQLite syntax: there are no enum types (use `TEXT` with a `CHECK`), and JSON goes in `TEXT` with `CHECK (json_valid(...))`. Index names are global per database, so prefix them with the table name (`<table>__<column>_idx`). Every `up` script needs a matching `down` script.
- **Plugins are language-agnostic, on purpose.** flwrs is meant to support a varied ecosystem of plugins written in any language. The contract between server and plugin is the wire framing plus `plugin/schema/*.proto`, specified in **`docs/protocol.md`** (protocol version 2), not the Rust SDK. So:
  - Proto conventions: every enum's zero value is named `UNDEFINED` (never `UNSPECIFIED`), so a value that was never set can't be mistaken for a real one. Enums are wrapped in a message (`message Foo { enum Enum { … } }`) to scope their value names. There are two files: `payload.proto` (package `flwrs.payload`: the typed payload model) and `protocol.proto` (package `flwrs.protocol`: `FrameHeader`, `MsgCode`, and one message per code, shared by all plugin types). Payload values are plain scalars in a `oneof`, not Google wrapper types. `plugin/src/schema/mod.rs` has tests that enforce the zero-value convention.
  - Treat the `.proto` files as a public, versioned API. Changes must be backward compatible: add new fields, messages and enum values; never renumber, reuse or change the type of an existing field number or enum value. Mark removed fields `reserved`.
  - Framing (`plugin/src/plugin/frame.rs`): the frame layout has its own version byte (`FRAMING_VERSION`, 2); changing the layout needs a new one. The `FrameHeader` message evolves like any proto (new fields are ignored by old readers; its `flags` bits must be negotiated first). A new `MsgCode` comes with a new capability or `PROTOCOL_VERSION`, so a peer never receives a code it doesn't know. Protocol v2 is the baseline (the text-header v1 was never released and isn't supported); from here on the hub must keep accepting older protocol versions when newer ones come.
  - Every protocol rule a plugin must follow is written down in `docs/protocol.md` (also posted for outside feedback: write it for readers who don't know the code). Keep it in sync when the SDK's or the hub's behaviour changes, and keep the conformance suite (`trellis/`) checking the rules.
  - Don't let Rust-only concepts leak into the protocol: anything a plugin must do or send has to be expressible in protobuf and plain TCP.
  - `flwrs-plugin` is the reference SDK, one implementation among many possible ones. Plugin behaviour the server relies on must be documented in `docs/protocol.md`, not just implemented in the Rust runners.
  - Plugins don't have to be Rust. A non-Rust plugin's source lives in `plugins/<name>/` with its own build files. It's simply not listed as a workspace member; nothing else is needed.
  - `examples/plugins/` holds demo plugins in other languages (Python, Go, TypeScript, Java). They're deliberately minimal and unsupported: keep them small, in sync with protocol changes, and out of the Cargo workspace.

## What flwrs is

flwrs is a framework and server for running pluggable workflows (data flows), inspired by [Node-RED](https://nodered.org/). Users build workflows from pre-compiled modules (plugins) and configuration, not by writing code. Goals:

- **Lightweight and scalable:** the same runtime runs in a data centre and at the edge.
- **Flexible:** from simple automation up to complex pipelines, for example running ML models as workflow steps.

### Plugin model

- Each plugin is a **separate executable, in any language**. The server launches it as a child process. The plugin then connects back to the flwrs runtime (the "hub") over TCP, using the host and port given on its command line. The connection is usually loopback, but plugins can also run on other machines (distributed deployment).
- Any executable that speaks the wire format below and the messages in `plugin/schema/*.proto` is a valid plugin. The full spec for plugin authors is `docs/protocol.md`; `cargo run -p flwrs-trellis -- <package folder>` checks a plugin against it.
- There are three plugin types:
  - **Source:** produces events, such as a trigger or an input.
  - **Transform:** takes in events and emits changed events.
  - **Sink:** consumes events, such as sending an HTTP request.
- The first frame on every connection is the plugin's `Initialize`: its instance id (`--id`), version, type, `token` (from `FLWRS_TOKEN` or `--token`; empty for mTLS nodes), the schema of its input and/or output payload (`SchemaDefinition`), the protocol versions it speaks and its optional capabilities (`ACKS`, `CREDITS`).
- **Wire format:** `u32 LE packet length` + `u8 framing version` (2) + `u32 LE header length` + a protobuf `FrameHeader` + a protobuf body. `FrameHeader.code` (`MsgCode`) names the body's message; for `EVENT` frames the header also carries `seq` (per connection and direction), `input_seq` (a transform output's input), the hub's `EventMetadata` and the delivery `attempt`, so the hub routes bodies without decoding them. The framing lives in `plugin/src/plugin/frame.rs` and is public (`read_frame`, `read_frame_limited`, `write_message`, `encode_frame`, `Frame::decode`, the `WireMessage` trait), so the hub reuses it.
- **Lifecycle:** the hub answers `Initialize` with `InitializeResponse` (protocol version, enabled capabilities, heartbeat interval, consumer window) or `Shutdown { reason }` (rejected). Data flows only after `InitializeResponse`. Both sides answer `PING` with `PONG`; the hub pings every 10 s and a silent side may be dropped after three intervals. With `CREDITS` a producer sends events only against `Credit` grants; with `ACKS` both sides `ACK`/`NACK` events by seq (consumers within their `max_unacked` window), and the hub redelivers unacked events. The plugin reports failures as `ErrorEvent`s and its logs as `LogEvent`s, and answers `Shutdown` with `Exit`. If the connection drops, the SDK runners reconnect with backoff (1 s doubling to 30 s, jitter) and re-send the cached `Initialize`; `Shutdown` before `InitializeResponse` makes `run` return `Error::Rejected`.
- **Event metadata** (event id, trace id, hops, origin node, create time) is the hub's: it's in the header of events the hub sends, and producers never set it. A transform's output names its input in `input_seq` and the hub continues that input's trace (it remembers unacked inputs and the last 1024); `input_seq = 0` starts a new trace (e.g. an accumulator emitting on a timer).
- Payloads are lists of typed `Field`s. Supported types: string, i32, u32, i64, u64, f32, f64, bool, datetime, bytes (optionally with a schema `content_type`), array, map (all values share one type), object (named fields with their own types) and packed numeric arrays (`PACKED_F32` … `PACKED_U64`). A `FieldValue` with nothing set means null. Values and schemas nest at most 32 levels.

### Glossary

- **Scene:** a stored workflow definition: a name, an optional hop limit, and a graph of nodes and edges. Persisted in SQLite, exposed through REST, and portable between servers as a `.flwr` file (export / import).
- **Director:** runs the enabled scenes (`app/src/modules/director/`): loads each scene's graph, starts its nodes through the supervisor, and routes events between them through bounded queues. It also runs the hub.
- **Hub / runtime:** the server side that plugins connect to (`app/src/modules/hub/`): the TCP listener, the handshake and the per-connection reader and writer. The director tells it which nodes to expect (`Hub::expect` → `NodeLink`).
- **Supervisor:** runs one plugin instance per node (`app/src/modules/supervisor/`): launches local plugins as child processes, health-checks and relaunches them, waits for remote ones, and runs the shutdown sequence.
- **Instance id vs plugin id:** in the protocol, `plugin_id` (in `Initialize`, events, logs) is the **instance** id: the node id passed as `--id` for local plugins, or a remote node's `config.remote_id` (falls back to the node id). In the DB and REST API, `plugin_id` on a node is the installed plugin package's id. The node id changes when a scene is imported elsewhere; a `remote_id` doesn't, and isn't unique (the token tells nodes with the same `remote_id` apart).
- **Nodes and plugins** aren't linked by a foreign key (since `1.0.0-5`): an imported scene may name plugins this server doesn't have. The scene service's `check` reports such problems, and enabling is refused until there are none. Deleting a plugin that nodes use is still refused (checked in the same write transaction as the delete).

### `core/` — `flwrs-core` (library)

Infrastructure shared by the server and by future binaries.

| Path | Description |
|---|---|
| `src/lib.rs` | Module exports. |
| `src/args.rs` | CLI args (`clap`): `-c/--config <path>`, default `config.toml`. |
| `src/config.rs` | `Source` trait for reading config by key path (`read_string`, `read_int`, `sub`, …). `main_config()` is a lazy global loaded from the CLI config path; the process exits if the file is missing or invalid. `read_struct::<T>()` deserializes a section into a struct. |
| `src/config/toml_source.rs` | TOML implementation of `Source`. |
| `src/logging.rs` | Logging config types (`[logging]` section: `id`, `format`, `level`, `sinks`). `init_main_logger()` installs the logger and sets the `log` max level; call it first thing in `main`. If the section is missing or invalid, it falls back to a console logger at INFO. |
| `src/logging/loglog.rs` | `LogLogger`: a `log::Log` that fans records out to several sinks: console and rotating file (via `flexi_logger`), and syslog. |
| `src/db.rs` | `Database` enum (SQLite only for now), `DbError`, and `build_db(name, ups, downs, version)`, which opens the DB from the `[db.<name>]` config and runs migrations. |
| `src/db/migrations.rs` | `MigrationDef` parses migration file names shaped `MAJOR.MINOR.PATCH-BUILD.{up,down}.sql` and hashes their contents. `Version` holds the parsed version; its `Ord` compares major, then minor, patch and build number. |
| `src/db/sqlite.rs` | SQLite pool setup (`sqlx`; WAL journal, 5 s busy timeout) and the `Migrator`. Each migration runs in its own transaction and is tracked in the `migrations` table. If an upgrade fails, the migrations applied earlier in that run are rolled back with their `down` scripts. |
| `src/http.rs` | `HttpServer`, an `axum` server registered as a service. API routers are nested under `/api`; root routers (for example Swagger UI) are merged at `/`. Reads its settings from the `[http]` section (`host`, default `0.0.0.0`; `port`, default `80`). |
| `src/registry.rs` | `ServiceRegistry` and the `Service` trait (`id`, `start(shutdown)`): starts every registered service, cancels them on Ctrl+C (or SIGTERM on Unix) and waits for them to stop. |
| `resources/migrations/sqlite/migrator.sql` | Schema of the migrator's own `migrations` tracking table. |

**Pattern for a new app module:**
- `modules/<name>.rs`: `init(...)` called once from `main.rs`, then `service()`.
- `<name>/service.rs`: logic, models and error type.
- `<name>/service/query_sqlite.rs`: queries taking `&mut SqliteConnection`, so they work in transactions.
- `<name>/api.rs`: an axum router with `State<&'static Service>`, so tests can build it with their own service. Errors via `api_error::ApiError`, plus a `utoipa` `OpenApi`.

Then wire the router into `app/src/http.rs`, and add migrations under `resources/migrations/sqlite/main/`. Tests use `db::test_db()`, plus the fixtures in `plugin::service::tests` / `scene::service::tests`.

### `plugin/` — `flwrs-plugin` (plugin SDK, `cdylib` + `rlib`)

The protocol definition (`schema/`), plus the reference Rust SDK for implementing it. Plugins in other languages generate their own code from `schema/*.proto` and implement the framing themselves.

| Path | Description |
|---|---|

| `schema/protocol.proto` | `flwrs.protocol`: `MsgCode`, `FrameHeader`, `EventMetadata`, `PluginType`, `Capability`, and one message per code: `Initialize`, `InitializeResponse`, `Event`, `Ack`, `Nack`, `Credit`, `Ping`, `Pong`, `LogEvent`, `ErrorEvent`, `Shutdown`, `Exit` (+ `ExitCode`, `LogLevel`). |

| `src/plugin/core.rs` | Builder types `InitializeRequest` (`into_initialize(type)`: protocol 2..2, ACKS + CREDITS), `SchemaDefinition` and `FieldDefinition` (`with_content_type`). `InboundEvent` (seq, attempt, metadata, payload; `input_ref()` → `InputRef`). `ConnectionConfig` (host, port, optional token, `ReconnectPolicy`, `tls` with the feature), `TOKEN_ENV` (`FLWRS_TOKEN`) and `MAX_RECONNECT_DELAY` (30 s, the protocol maximum). |

| `src/plugin/tls.rs` | (feature `tls`) `TlsSettings` (CA file, server name, client cert + key; `from_env`: `FLWRS_TLS_CA`, `FLWRS_TLS_SERVER_NAME`, `FLWRS_TLS_CERT`, `FLWRS_TLS_KEY`), `ClientTls` (rustls/ring). |

| `src/sink/{plugin,runner}.rs` | `Sink` trait (`initialize`, `async fn consume_event(&self, InboundEvent)`, `shutdown`, `version`) and `SinkRunner` (`SinkRunnerConfig::new`, `max_unacked` 16, `max_concurrent` 1 = in order; `with_max_unacked` / `with_max_concurrent`): `run` connects, sends `Initialize`, runs up to `max_concurrent` events at once and acks each by its seq when its future finishes (NACK on error; `SinkError::retryable` → retry); on `Shutdown` it finishes the events already received first; on a disconnect unfinished ones are dropped (the hub redelivers). | `src/source/{plugin,runner,local_sink}.rs` | `Source` trait: `initialize` receives a cloneable `LocalSink`, and `async fn run` emits events through it (`emit`: waits for credit; `emit_confirmed`: also waits for the hub's ACK). `SourceRunner` starts `run` only after `InitializeResponse`, cancels it on `Shutdown` or a disconnect, restarts it after a reconnect, and restarts it with a backoff if it fails. |

| `tests/` | Integration tests that drive each runner against a fake hub over TCP (`tests/common`): handshake fields, acks and nacks, no acks without the capability, ping and the heartbeat timeout, hub restart and re-initialize, rejection, protocol violations, credits, `emit_confirmed`, transform outputs and their acks, logs before `Initialize`. The logger is process-wide, so each file is its own process and tests within a file run one at a time; every wait has a timeout. |

**To write a Rust plugin:** create a binary crate under `plugins/`, add it to `members` in the root `Cargo.toml`, and depend on `flwrs-plugin.workspace = true`. Implement `Sink`, `Source` or `Transform`, declare the schema with the `core.rs` builders, parse `--id/--host/--port/--log-level` (and an optional `--token`; the runner falls back to `FLWRS_TOKEN`) and run the matching `*Runner`. Keep `-h` free for `--help`. `plugins/http_sink` is the reference example.

### `plugins/` — base plugin library

| Plugin | Type | Description |
|---|---|---|
| `http_sink/` (`flwrs-http-sink`) | Sink | Sends an HTTP request for each event, built with `reqwest`. Payload fields: `url` (string), `method` (string), `headers` (map → array of strings), `body` (string or bytes). CLI flags set the timeouts, verbose logging and `--max-concurrent-requests` (16). Each event is acked after its response (success status); network errors, timeouts, 408, 429 and 5xx are NACKed retryable, other failures not. Exits with status 1 if the run fails or the hub rejects it. Package files: `manifest.json`, `schema/launch_args.json`, `schema/in.json`; tests keep them in sync with the code (version, input schema, CLI flags). |

**Plugin packages.** A plugin is distributed as a ZIP with `manifest.json` at its root, the executable it points to, and the schema files it references (format in README.md, *Plugin packages*). Rust plugins in this repo are packaged with `cargo xtask package-plugin <dir>` → `target/plugins/<id>-<version>-<platform>.zip` (the host platform is written into the manifest). A Rust plugin that's packaged needs a `manifest.json` next to its `Cargo.toml`, with the same version.

### `examples/plugins/` — demo plugins in other languages

One folder per example, each self-contained (`manifest.json`, `schema/in.json` with `url` / `method` / `body` strings, `build.sh` → `dist/<id>-0.0.1.zip`; generated code and build output are gitignored). `README.md` there lists what they implement and leave out. Protos are read from `../../../plugin/schema/`.

|---|---|
| `http_sink_python_example/` | `plugin.py` (shebang executable), code generated into `gen/` by `grpcio-tools`; the host needs `protobuf`. |

### `trellis/` — `flwrs-trellis` (the conformance suite)

| Path | Description |
|---|---|
| `src/lib.rs` | `Target` (from a package folder's `manifest.json`), `run(target, only)` → `CaseResult`s, `CASES` (handshake, waits-for-acceptance, answers-ping, data-events, shuts-down, stops-when-rejected, reconnects, closes-on-violation), `sample_payload(schema)`, `report`. Each case starts the plugin afresh against a fake hub (which grants and returns credit like the hub). |
| `src/main.rs` | CLI: `flwrs-trellis <package folder> [--case …] [--list] [-- plugin args]`; exit 1 on a failure. |
| `tests/sdk_plugins.rs` | The SDK's sink, source and transform (this test binary as a child) must pass every case; a plugin that never connects must fail. Unix-only. |

When the protocol changes, update the suite with it, and run it against `http_sink` (packaged with `cargo xtask package-plugin http_sink`) and the demos.

## Current state / known gaps

This is early-stage code. Keep these in mind before relying on the behaviour:

- **Single node only:** one server runs every scene it has. There's no clustering: no sharing scenes across servers, no failover or handover of scenes between servers, no load balancing. Remote plugins can run on other machines, but they all connect to one hub.
- **Plugins and UI:** the base plugin library has one plugin (`http_sink`), plus the unsupported demos in `examples/plugins/` (they pass the conformance suite, but aren't in the automated tests: that would need their toolchains in CI).
- **Conformance suite:** doesn't check yet the heartbeat timeout, size and nesting limits, or redelivery behaviour. Scenes are managed through the REST API only; there's no web UI yet.

- **Remote links:** TLS (and mTLS) is available through `[hub.tls]`; the plain listener stays for local plugins and for remote token nodes with `require_tls = false`. Certificates aren't reloaded without a restart, and there's no revocation (CRL) check.
- **Process trees on Unix:** the plugin's whole process group is signalled while the plugin runs. If the plugin itself dies first, processes it started that are still running aren't cleaned up (on Windows the Job Object kills them).
- **Windows:** the Windows-specific code is type-checked and linted for `x86_64-pc-windows-msvc`, but there's no Windows CI, and the process tests are Unix-only (they use shell scripts). Run them on Windows (with `.cmd` equivalents) before relying on it.
- **Director / delivery:** at-least-once for plugins with `ACKS` (redelivery after disconnects, crashes and retryable NACKs, dead letters after `max_attempts`); at-most-once for plugins without it. Memory and spill queues lose their events on a server restart; durable queues don't (they're replayed), but a durable queue's events are lost if its node's queue kind changes on a reload, and producers' events written but not yet committed when the server stops are lost unless the producer resends after its unanswered `emit_confirmed`. Reloads are diffs: only changed nodes restart, and a changed node keeps its queue. Status: `GET /api/scenes/by-id/{id}/status` and `GET /api/status`; counters are in memory, per node, and restart when the node does; history only through the telemetry sinks (OTLP or files; the server has no query API for the files, and no Prometheus scrape endpoint).
- **Spool queues and the hub-wide disk limit:** a `block` push to a spill or durable queue that waits only for room under `[director] spill_max_bytes` is woken by its own queue's changes (writes, deletes, purges), not when another queue frees spool space. It rechecks at its queue's next change or gives up at `block_timeout`, even if room appeared sooner. Fixing it would need a shared wake-up on the spool gauge, which wakes every blocked spool producer on each release; left as is, since it only matters when the hub-wide limit is the bottleneck.
- **Mappings:** dot-notation and Lua work end to end (saved, checked against the plugins' schemas, evaluated by the director, exported and imported). A server built without `mapping-lua` refuses Lua when saving, and lists it as a problem in `check` (imports go through; enabling is refused; the director won't start such a scene). Lua calls run on the router task: a script near its time limit delays that producer's other events. A plugin upgrade doesn't re-check mappings; one that no longer fits shows up in `check` and makes the scene fail on its next load.
- **Bulk graph edits:** each node or edge change is its own transaction, and reloads an enabled scene (a diff; queued reloads are applied once). To restructure a live scene in one step without intermediate states running, disable it, edit, then enable it again.
- **SDK restarts:** inside a plugin, a source whose `run` keeps failing is restarted every second indefinitely, and reconnects retry forever. The supervisor's limits (`reconnect_timeout_ms`, `max_restarts`) bound this from the outside for local plugins.
